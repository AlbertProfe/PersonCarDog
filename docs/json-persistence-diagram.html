JSON Persistence Explained

How PersonCarDog saves the in-memory Repository to a JSON file
and why this is the perfect bridge to Spring Boot + JPA

Core idea: The Repository acts as an in-memory database. JsonStore is the “disk” layer that serializes the whole database into a single JSON file (data/repo.json) and restores it later. This is exactly the role a real database (H2, PostgreSQL…) plays in Spring Boot.

2. Why do we need a Snapshot (DTO)?

Domain objects have object references (Person → Car, Person ↔ Dog). If we serialize them directly with Jackson we get:

  • Infinite recursion (Person → Dog → Person → …)
  • Duplicated objects inside transactions & adoptions

Solution: convert the object graph into a flat, ID-based structure (exactly like foreign keys in a relational database).

3. SAVE Flow (Repository → JSON file)

ServicesaveRepository()
→
JsonStore.save
→
toSnapshot()entities → DTOs
→
JacksonwriteValue()
→
data/repo.json
  1. Service calls JsonStore.save(repo, path)
  2. toSnapshot() walks every list in the Repository and builds flat DTOs, replacing object references with id strings (foreign-key style).
  3. Jackson’s ObjectMapper writes the Snapshot as pretty-printed JSON.
  4. Parent directories are created automatically if needed.

4. LOAD Flow (JSON file → Repository) — Two-Pass Strategy

data/repo.json
→
JacksonreadValue()
→
RepositorySnapshot
→
fromSnapshot()2 passes
→
Repositoryready

Pass 1 — Create entities

  1. Instantiate every Car, Person, Dog with the persisted ID
  2. Put them into temporary Maps keyed by ID
  3. Add them to the Repository

At this point references are still null / missing.

Pass 2 — Wire references

  1. Look up each entity by ID from the Maps
  2. Set person.car, person.dog, dog.owner
  3. Rebuild CarTransaction & DogAdoption objects with real object references

Now every relation is a single shared instance (no duplicates).

Why two passes? You cannot set a reference to an object that does not exist yet. First create everything, then connect the dots — the same strategy ORMs use when loading bidirectional associations.

7. Teaching Takeaways for Spring Boot

  • Repository = in-memory DB → later becomes a real JPA Repository.
  • Snapshot DTOs = foreign keys → in Spring you will use @ManyToOne / @OneToOne and the ORM does the ID mapping for you.
  • Two-pass load → Hibernate does the same thing when it materializes the object graph from SQL result sets.
  • Bidirectional relations (Person.dog ↔ Dog.owner) must stay consistent — in JPA you will use mappedBy and cascade options.
  • JsonStore.save / load → later replaced by automatic dirty checking + entityManager.persist() / flush().
Bottom line for students:
You are already implementing the core persistence concepts (object graph → flat storage → object graph) with pure Java + Jackson. When you move to Spring Boot you will keep the same domain model and simply let JPA/Hibernate handle the Snapshot and the two-pass loading for you.
